# 開発・AIコーディング指示書 (INSTRUCTIONS.md)

本ドキュメントは、今後AIや開発者が本プロジェクト（`MyNKF`）のコードを修正・追加する際に遵守すべきコーディングスタイル、エラーハンドリング方針、設計原則、および出力フォーマットについて規定するものです。

---

## 1. 命名規則

Rustの標準的なコードスタイルガイドラインに従います。

| 対象 | 規則 | 例 |
| :--- | :--- | :--- |
| **変数、関数、メソッド、引数、モジュール** | `snake_case` (小文字＋アンダースコア) | `guess_encoding`, `to_enc`, `utf8_score` |
| **型、構造体、列挙型、トレイト** | `PascalCase` (単語の頭文字が大文字) | `Encoding`, `LineEnding`, `MyNkfGuiApp` |
| **定数、スタティック定数** | `SCREAMING_SNAKE_CASE` (大文字＋アンダースコア) | `MAX_GLOB_FILES`, `JIS_TO_UNICODE_BASE64` |
| **マクロ** | `snake_case!` | `todo!`, `matches!` |
| **ドキュメント・ファイル名** | `UPPER_SNAKE_CASE` (大文字＋アンダースコア) | `ARCHITECTURE.md`, `INSTRUCTIONS.md`, `README_JA.md` |

- **ドキュメントの命名規則**: プロジェクトルートおよび `docs/` 配下の Markdown ドキュメントファイル名は、全て大文字のスネークケース（例: `README_JA.md`, `TEST_REPORT.md`）に統一すること。

## 2. エラーハンドリングの方針

低リソース環境下での常駐や連続処理を想定しているため、堅牢なエラーハンドリングを重視します。

- **パニックの回避**: ライブラリ（`src/lib.rs`）およびGUI版（`src/bin/mynkf-gui.rs`）において、`unwrap()`、`expect()`、`panic!` の使用は極力避けてください。ファイルの読み書きエラーや、文字コードの不整合によってアプリケーション全体がクラッシュしないように実装します。
- **戻り値によるエラー伝播**: エラーが想定される処理では、`Result<T, E>` や `Option<T>` を戻り値として返し、上位でエラーハンドリングまたはログ出力を行ってください。
  - コアライブラリでは `Result<(), String>` や `Option<(u8, u8)>` などの分かりやすい型を返します。
  - CLI版（`src/main.rs`）のエントリーポイントでは、`std::io::Result` を戻り値として返し、エラー時は `eprintln!` でエラーを出力した上で、終了ステータス `1` で正常にプロセスを終了します。
- **文字マッピング失敗のフォールバック**: マッピングテーブルに存在しない外字や特殊文字が検出された場合、変換をエラーで中断するのではなく、`??`（2つのクエスチョンマーク）などの安全なデフォルト文字にフォールバックして処理を継続する仕様とします。

## 3. コンポーネント・モジュールの分割基準

コードサイズとビルドのフットプリントを最小限にするため、適切な境界でモジュールを分割します。

- **`src/lib.rs` (コアライブラリ)**:
  文字コードの自動判定、デコード・エンコード、改行コードの検出、ワイルドカード展開など、「入出力データそのものの加工・解析」に関わる純粋な関数を集約します。このモジュールは外部依存を一切持ちません。
- **`src/main.rs` (CLIエントリーポイント)**:
  引数のパース、ファイルおよび標準入出力のストリームの読み書き、結果の画面出力といった「コマンドラインのI/O処理」のみを担当します。
- **`src/bin/mynkf-gui.rs` (GUIエントリーポイント)**:
  `eframe` / `egui` UIの描画、`rfd` ファイルピッカーとの連携、Win32 APIを直接操作する FFI 定義など、「グラフィックとOS連携」を担当します。
- **共有機能のライブラリ集約**: フロントエンド（CLI/GUI）で重複する処理が発生した場合は、必ず `src/lib.rs` に関数を抽出し、再利用可能にしてください。

## 4. AIの出力・対話フォーマット

AIが変更作業およびコード提案を行う際は、以下の要件を満たす必要があります。

- **解説は最小限に**: 修正や追加を行うコードについて、実装の背景や設計思想に焦点を当てた簡潔な説明にとどめ、自明なコード説明などの冗長なテキストは避けてください。
- **直接適用可能なコード出力**: 置換や追加がスムーズに行えるよう、ファイル名、修正範囲の行番号、および前後のコードブロックが明確に分かる形でコードを提示してください。
- **日本語による詳細なRustdocコメントの整備**:
  公開APIや主要な構造体、関数を追加・修正する際は、必ず日本語のRustdocコメント（`///` や `//!`）をセットで更新・追加してください。コメントの書き忘れや、コードの実装との乖離（ドキュメンテーションの陳腐化）は許容されません。
- **ドキュメントの自動更新ルールの遵守**:
  ソースコードに変更を加えた際は、開発ガイドラインである `.agents/AGENTS.md` の「ドキュメント自動更新ルール」に基づいて、関連ドキュメント（`CHANGELOG.md` や `docs/SPEC.md` など）を同期して更新してください。
